# 当前方法说明：不含生成式规划器的 Laya 机器人 Agent

## 到底做什么
把机器人反复“读指令、判断条件、决定下一技能”的生成式语言推理，改成一批语义判断题和一个轻量的约束任务图；看图和执行技能仍然需要各自组件。

## 实际调用链
当前相机RGBD -> DINO检测/颜色和几何证据 -> NativeCompiler/ScopeCompiler -> Laya两阶段批量判断 -> min融合与约束候选任务图 -> 选一个已有技能 -> 原CaP-X控制/PyRoKi -> 新相机反馈 -> 下一轮。

不是：拿Laya输出一个概率，就把它当成抓取成功率。
不是：暗中用另一个生成式模型来出题、聚合或失败回退。
也不是：当前系统已经能处理所有物体、所有技能和任何自然语言任务。

## 谁出题
worker.py中的NativeCompiler扩展ScopeCompiler。semantic_core.py负责从当前对象和可用技能提候选，question_direct.py与question_scope.py提出有来源、作用域和条件绑定的题。
第一批判断动作是否被要求、物体是否受保护、指令是否取消、条件是否相关等；再根据第一批结果生成动作—条件、动作—动作顺序问题。
上下文保留原始指令和证据。问题会随对象、候选动作、条件及反馈改变，不是所有场景固定同一张问题表。
但它目前仍是规则/目录驱动的动态编译器，并不是开放词汇、任意技能的通用自动出题器。陌生对象和没接入的操作可能触发澄清。这是后续要验证和改进的边界。

## Laya负责什么
对语义选择题返回全部选项分数。当前使用已有T4适配权重和其校准，既非在线训练，也不是公共原版未经适配的成绩。
第一阶段和第二阶段都保留原始概率及问题，便于定位哪一个作用域、否定或依赖判断出错。
它不生成轨迹，也不读取仿真的任务真值。

## 聚合器负责什么
aggregation.py的GuardCheckedAggregator不是另一个神经网络。
它用有限宽度24的候选任务图，保留动作角色、保护、条件绑定和先后顺序的可能解释。
融合使用min等排序势，图分数用log支持度相加；这不是把相关回答假装成独立概率，亦不声称图分数是校准后的联合正确概率。
- 请求移动和明确保护冲突时不发动作。
- 依赖/条件未观测时请求观察；语义歧义时请求澄清。
- 在保留解释一致支持的可执行节点中选下一技能。
- 执行返回并不代表成功，必须核对新的视觉关系。
- 恢复使用Laya的反馈判断并遵守同一十轮预算，没有生成式LLM兜底。
当前完整概率相对硬标签没有已证明的额外收益，不能把“保留全部概率”本身当论文结论。

## 为什么可能快
快的来源应该是减少自回归输出和反复长规划，而不是缩短动作等待、换一个更容易的任务、让失败尽快结束。
动态出题、Laya批处理、融合、重新观察和恢复都有成本，必须计入。
相机、运动、初始化的共享工程优化必须同时给比较组；这些不是Laya算法独享收益。
使用同服务器常驻开源模型、简短结构化输出、计划缓存、共享技能，才更接近能检验真实优势的对照。

## 现在能说到哪一步
当前冻结T4在四种原生任务的新32初态完成32/32；这些结果不是任意陌生语义的通用性证明，也不是冻结128TEST结果。
旧Codex包含CLI、桥接、网络等耗时，不能把它的墙钟比例当成Laya相对本地模型的算法倍率。
本地开源模型对照单独存放，不进入这个代码包。结果出来前不能承诺“不损失成功率且固定加速几倍”。
本包整理运行核查仅证明整理后的入口能按预期运行，不增加泛化实验样本数。

## 后续工作的顺序
1. 同平台同任务的强开源短计划基线，先确认端到端时间与成功率。
2. 问题契约和作用域：输出格式包装、临时步骤、最终目标、否定、改口不要混淆。
3. 聚合与记忆：多种合理解释、合法条件、顺序和恢复预算，不让旧位置代替当前观察。
4. 视觉—语义—技能配合：漏检、遮挡再观察、对象身份、TCP和完成判定。
5. 扩展不同物体/语言改写/干扰/失败恢复，固定独立测试，不根据效果删除场景。
模型适配训练只是有证据需要时的选项，不是每次失败的默认处理。
